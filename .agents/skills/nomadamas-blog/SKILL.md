# NomaDamas 블로그 글

NomaDamas 블로그 글 한 편을 주제 선정부터 발행 확인까지 끝낸다. 글의 화면과 수치는 직접 설치하고 써 본 결과에서 가져온다.

블로그 스튜디오에서 다른 조사 세션을 이어받은 글은 `request.md`, `handoff.md`, `task.md`를 먼저 읽는다. 이 세 파일은 스튜디오가 전달한 현재 작업 계약이며, 조사 세션의 대화 전체를 복사한 기록이 아니다. `handoff.md`에 적힌 조사 파일·폴더와 기존 Herdr pane을 확인한 뒤, 그 자료에서 확인된 사실만 브리프의 근거로 사용한다.

기존 조사 세션에 새 글 작업을 전달할 때는 기존 작업을 덮어쓰지 않는다. 새 글의 목적, 스튜디오 작업 폴더, `handoff.md` 경로를 분명히 하고, 조사 세션의 결과물을 읽거나 인용하는 범위에서만 이어간다. 원본 세션이 아직 다른 작업을 진행 중이거나 pane·자료 경로를 확인할 수 없으면 메시지를 반복하지 말고 스튜디오에 상태를 묻는다.

글 한 편이 아니라 블로그의 검색 노출을 점검하거나 잴 때, 검색 수요로 글 주제를 찾을 때는 아래 흐름 대신 `references/search-audit.md`를 따른다. 거기서 고른 글 후보는 흐름 2단계로 넘긴다.

## 먼저 읽는 문서

이 스킬이 들어 있는 블로그 에디터 저장소가 작업 절차와 스킬 파일의 정본이다. 시작할 때 아래를 읽는다.

이 스킬은 세션을 연 체크아웃의 사본으로 불린다. 그 체크아웃이 옛 브랜치에 있으면 이 저장소에서 `git fetch origin` 뒤 `git diff --quiet origin/main -- .agents/skills/nomadamas-blog`가 실패하는지 확인한다. 차이가 있으면 `origin/main`의 스킬 파일을 다시 읽고, 이 스킬을 고치는 worktree라면 그 사본을 쓴다.

- 이 저장소의 `AGENTS.md`: 블로그 frontmatter, 본문 관례, 이미지, 작성자 표시와 발행 경계. 이 스킬과 겹치면 저장소 지침을 따른다.
- 이 저장소에 함께 있는 플레이북·브랜드·조사 문서: 파일이 있을 때만 해당 절을 읽는다. 이 저장소 밖의 경로를 정해 두고 찾지 않는다.
- 스튜디오 handoff가 있으면 `handoff.md`에 적힌 조사 파일·폴더: 기존 세션의 조사 결과와 근거를 재사용할 때만 읽는다.

글에 대한 결정은 이 저장소의 플레이북과 `AGENTS.md`가 정본이다. 조사 문서는 시작할 때 전부 읽지 않고, 이 스킬이나 저장소 지침이 가리킬 때 그 절만 연다. 사용자가 고쳐 준 지점은 이 스킬의 교정 표에 쌓는다(아래 사용자 교정 받기 절).

## 승인 경계

스튜디오가 기존 조사 세션을 이어받는 것은 컨텍스트 전달이지 발행 승인이 아니다. 기존 세션에 메시지를 보내거나 조사 자료를 개인 데이터로 다시 실행하는 일은 각각 별도 승인 경계를 따른다. `handoff.md`의 경로가 없거나 기존 pane의 소유·상태를 확인할 수 없으면 새 메시지를 보내지 않고 확인 가능한 자료만 사용한다.

아래는 대상과 금액을 밝히고 따로 승인받는다. 방향 동의나 항목 선택은 실행 승인이 아니다.

- 유료 API 호출: 키 이름과 금액 상한. 이미지를 찾는 `tvly` 검색은 여기 들지 않는다.
- 사용자의 실제 메일, 메신저 같은 개인 데이터로 돌려 보기. 결과는 로컬에만 두고 글, 커밋, 캡처에는 합성 데이터만 쓴다.
- push, PR 생성, 머지. 머지하면 바로 배포되므로 머지가 곧 발행이다.
- 웹마스터 도구의 계정 등록과 사이트 제출(사이트맵 제출, 색인 생성 요청, IndexNow를 손으로 다시 보내기): 건마다 대상 주소. 새 글의 색인 생성 요청은 머지 승인을 묻는 같은 질문에서 주소를 밝혀 받을 수 있다. 머지가 이미 끝났으면 따로 묻는다.
- 다른 저장소 이슈, 댓글, 피드백 전송.

참고 글 조사는 읽기만 한다. 조사 에이전트 프롬프트에 좋아요, 댓글, 폼 제출 같은 쓰기 요청 금지를 적는다. 남의 블로그에 남긴 반응은 되돌리지 못할 수 있다.

## 흐름

아래 체크리스트를 응답에 복사해 진행 상황을 표시한다. 건너뛴 단계는 이유를 적는다.

1. [ ] 자료 찾기: `handoff.md`가 있으면 먼저 읽고, 거기에 적힌 조사 파일·폴더와 기존 세션의 확인된 결과를 우선 검토한다. 찾을 곳은 주제마다 다르므로 사용자가 준 자료와 링크, 이전 세션(`session-history`), 이 저장소의 초안과 실험, 소개할 저장소의 README와 릴리스, 참고 글을 주제에 맞게 고른다. 기존 세션의 대화는 원본 pane과 자료 경로를 확인할 수 있을 때만 참고하고, 확인되지 않은 기억이나 요약을 사실로 쓰지 않는다.
2. [ ] 주제 정하기: 후보마다 근거(star 수, 블로그에 이미 있는 글, 최근 릴리스)를 붙여 내고 사용자가 고르게 한다. 요청에 블로그가 특정되지 않았으면 NomaDamas 블로그가 맞는지 같은 질문에서 확인한다.
3. [ ] 목차 확인: 먼저 플레이북 2~7절을 다시 읽고 글 유형, 절마다 넣을 화면, 저장소 링크의 자리를 그 결정에 맞춘다. 그림과 틀은 이 단계에서 정해져서 원고 단계에 읽으면 늦다. 독자, 글 유형, 검색 키워드, 이 글이 남길 한 문장, 절 목록, 절마다 넣을 화면, 아래 점검 세 가지의 답을 사용자에게 확인받은 뒤 쓴다. 글 유형이 어긋난 원고는 고치는 것보다 다시 쓰는 비용이 크다.
    - 기준 독자를 실제 동료나 구체적인 독자상으로 잡고, 아는 용어와 설명이 필요한 용어를 나눠 적는다. 직업이 같아도 배경지식이 같지는 않다.
    - 점검 1: 내세울 차이가 독자가 쓰는 대안에도 이미 있는지 대안의 1차 출처로 확인한다. 있으면 다른 차이를 세운다. 확인하지 않으면 제목이 내세운 차이를 본문의 비교가 스스로 부정하게 된다.
    - 점검 2: 독자가 도착할 저장소의 README 첫 화면, 설치 한 줄, 열린 이슈가 글이 약속하는 첫 결과를 받쳐 주는지 조회한다. 어긋나면 글에서 그 간격을 메우고, 저장소를 고칠 일이면 이슈 제안 후보로 사용자에게 알린다.
    - 점검 3: 독자가 시작 전에 갖출 것(계정, 설치 환경과 버전, 비용, 걸리는 시간)을 공식 문서와 직접 써 본 값으로 적는다. 진입 장벽이 큰 독자는 빼지 않고 따라 하기와 준비 상자로 길을 낸다.
4. [ ] 직접 써 보기: 격리한 시연 폴더에 설치하고 실제로 쓴다. 시연 데이터, 시연 모델, 고친 빌드는 플레이북 8절을 따르고, 방법은 `references/hands-on-capture.md`의 시연 환경 절을 본다.
5. [ ] 캡처, 영상, 이미지, 표지: 절마다 보여 줄 것에 맞는 자료 후보를 플레이북 6절대로 모은다. 생성 이미지는 어느 것으로도 보일 수 없는 그림에만 쓴다. 찍고 구하는 방법은 `references/hands-on-capture.md`.
    - 원고를 쓰기 전에 절마다 쓸 자료를 `html-explainer`의 확인 시트 한 장으로 보이고 사용자가 고르게 한다. 자료의 형태와 자리에 대한 판단은 처음 겪는 상황마다 새로 나와 문서로 미리 정할 수 없어서, 발행 뒤가 아니라 이 자리에서 받는다.
    - 시트의 각 절에는 후보 실물을 그 자리에서 보고 듣게 넣는다. 이미지는 원본 크기로, 영상은 원본 소리를 켠 채, 문서는 넘겨 볼 수 있게 둔다.
    - 각 절에 자료를 둘 자리(절 머리, 본문 사이, 맺음)와 그 절의 링크 위치(저장소 GitHub 주소 등)를 함께 적는다.
    - 사용자가 고른 것 중 다른 글에도 맞는 판단은 아래 사용자 교정 받기 절대로 교정 표에 적는다.
6. [ ] 원고: 쓰기 전에 `corrections.py brief`로 지난 교정을 읽고, `references/review.md`의 독자와 도입 절을 적용한다. 글은 정보 나열이 아니라 독자의 장면에서 출발하는 이야기로 쓴다. 장면이 무엇인지와 사진 속 모습을 옮긴 문장의 기준도 플레이북 4절에 있다. 블로그 저장소의 글 브랜치에서 바로 쓴다. 블로그 빌드로 바로 미리 볼 수 있어 따로 미리보기 렌더러를 만들지 않아도 된다. 수치와 주장마다 근거를 근거 표에 남긴다(`references/review.md`).
7. [ ] 검수: 사실 대조, 독립 검토, 윤문, 군더더기 정리, AI 티 2차 탐지, 지난 교정 검사, 다른 글과 겹치는 문장, 검색 키워드 점검, 바뀌면 안 되는 것 확인 순서다. `references/review.md`. 검색 키워드 점검은 `references/seo-geo.md`.
8. [ ] 빌드와 미리보기: `references/publish.md`. 미리보기 주소를 사용자에게 알린다.
9. [ ] PR: 이번 글의 경로만 올린다. 테마를 고쳤으면 PR을 나눈다. `references/publish.md`.
10. [ ] 발행: 승인을 받아 머지하고 배포와 실제 페이지를 확인한다. `references/publish.md`. 그다음 IndexNow 결과를 보고 Google 색인 생성을 요청한다. `references/seo-geo.md`.
11. [ ] 공유: 사이트에 최신 수정이 올라간 것을 확인한 뒤 Threads(한국어), X(영어) 공유 글을 만들어 사용자에게 보인다. 게시는 따로 승인받는다. `references/share.md`.
12. [ ] 정리: 띄운 서버를 끄고 시연 폴더와 개인 데이터 사본을 정리한다. 이 저장소에서 `git branch --no-merged origin/main`으로 글 브랜치가 머지 없이 남았는지 보고, 남았으면 사용자에게 알린다. 고친 글이 로컬에만 남으면 사이트는 고치기 전 내용을 계속 보여 준다. 머지된 worktree와 원격 브랜치는 `references/publish.md` 작업 폴더 정리 절에 따라 지운다. 남은 후속 작업은 이 저장소 이슈로 연다.

## 사용자 교정 받기

어느 단계에서든 사용자가 원고, 이미지, 글의 방향을 고치라고 하면 아래 순서로 한다. 같은 지적을 두 번 받지 않으려는 것이다. 발행한 글이면 `references/publish.md` 발행 뒤 수정 절의 체크리스트로 진행한다.

1. `corrections.py list`로 같은 교정이 있는지 본다.
    - 있으면 이번이 두 번째 이상이다. 고치기 전에 무엇을 잘못 이해했는지 한 줄로 사용자에게 말하고 접근을 바꾼다. 같은 방식으로 다시 고치면 세 번째 지적이 온다.
2. 지적받은 곳과 같은 모양을 원고 전체에서 찾아 함께 고친다.
3. 교정 표 `references/corrections.tsv`에 적는다. 1에서 찾았으면 `hit`로 적고 `hit`이 알려 주는 다음 단계를 따른다. 없었으면 아래 둘을 정해 `add`로 적는다.
    - 유형(검사, 검토, 결정, 이 글만)은 `corrections.py --help`의 기준으로 고른다. 문장 모양으로 잡히면 검사로 적는다.
    - 검사 패턴을 적거나 바꿀 때는 `--scan <블로그 저장소>/src/content/posts`를 붙여 발행한 글에서 걸리는 곳을 본다. 고칠 문장이 아닌 곳이 걸리면 저장한 패턴을 좁힌다.
    - 검토 행에 `hit`할 때는 `--type 검사 --pattern`으로 올리거나 `--reason`으로 이유를 이번 경우까지 넓혀야 저장된다.
    - `reason`은 다른 글에도 맞는 원리로 적는다. 이번 글의 유형이나 자리(비교 글, 글 머리)에 묶어 적으면 다른 유형의 글에서 같은 지적을 다시 받는다. 이번 글의 문장은 `before`와 `after`에 남는다.
4. 결정 행은 플레이북에도 적고 규칙 끝에 그 id를 단다. 특정 글 유형의 묶음 안이 아니라 그 규칙이 맞는 가장 넓은 절에 둔다. id가 빠지면 `tests/`의 플레이북 대조 테스트가 실패한다.
5. 사용자에게 적은 id와 유형을 알린다. 사용자가 유형을 바꾸라고 하면 `edit`로 바꾼다.
6. [ ] 교정 표는 이 스킬 폴더에 있고 `corrections.py`는 스크립트 옆의 표를 읽고 쓴다. 기본 체크아웃이 다른 브랜치에 있어도 최신 `origin/main`의 스킬과 비교한 뒤 이 저장소의 작업 worktree에서 돌린다(`list`, `brief`도 같다). 고쳤으면 이 저장소의 해당 경로만 커밋한다.

## 작업물을 두는 곳

스튜디오 handoff로 시작한 글은 조사 원본을 복사하지 않고 경로를 근거 표에 남긴다. 조사 결과를 브리프나 원고에 사용한 사실마다 원본 파일·세션·확인 시각을 연결하고, 확인하지 못한 대화 내용은 추정으로 채우지 않는다. 스튜디오 밖에서 시작한 세션도 같은 형식의 `handoff.md`를 작업 폴더에 두면 이후 스튜디오로 넘길 수 있다.

- 원고와 이미지: 블로그 저장소 `src/content/posts/<slug>.md`, `src/assets/images/<slug>/`.
- 캡처 원본, 편집 스크립트, 로그, 합성 데이터 생성기, 근거 표, 윤문 전 사본(`before.md`): 이 저장소 `README.md`에서 정한 주제 소유자와 작업 폴더 규칙을 따른다. 기존 작업 폴더를 재사용하고 원본은 세션 임시 폴더에 두지 않는다.
- 블로그 원고와 작업 기록은 별도 clone이나 worktree에서 한다. 다른 세션이 기본 체크아웃을 쓰고 있을 수 있다. 이 저장소의 `AGENTS.md`와 `README.md`가 정한 브랜치, worktree, 커밋 규칙을 따른다. 세션이 다시 시작돼도 임시 폴더가 비워지지 않도록 영속 worktree에 둔다.

## 스크립트

- `scripts/render_terminal.py`: tmux로 뜬 터미널 화면(ANSI)을 강조 표시가 들어간 PNG로 렌더링한다.
- `scripts/render_html.py`: 표지와 설명 그림 HTML, 공개 웹 페이지를 PNG로 찍는다. 높이를 주지 않으면 아래 여백을 잘라 준다.
- `scripts/check_post_invariants.py`: 원고의 금지 기호, 이미지나 영상이 없는 절, 한 문단의 물결표 두 개를 찾는다. 두 파일을 주면 윤문 전후에 frontmatter 값, 코드, 이미지가 그대로인지와 새로 생긴 연결어미 뒤 쉼표를 보고, `--published`면 발행본과 고친 원고를 비교한다. `--commas`는 원고 하나의 연결어미 뒤 쉼표를 문맥과 함께 모두 보인다.
- `scripts/check_phone_width.py`: 빌드한 글을 폰 폭 iframe에 띄워 가로로 넘치는 요소를 잰다.
- `scripts/check_playback.py`: 빌드한 블로그에서 홈의 링크를 눌러 글로 들어간 뒤 본문 영상이 재생되는지, 소리가 있는데 `muted`인 영상이 없는지 본다.
- `scripts/check_live.py`: 발행한 글의 실제 페이지에서 응답, 작성자 표시, og:image, 본문 미디어, sitemap, 고친 문구와 지운 문구를 확인한다.
- `scripts/corrections.py`: 사용자 교정을 표에서 찾고(`list`) 적고(`add`, `hit`, `edit`), 쓰기 전 요약(`brief`), 검토자 점검표(`review`), 원고 검사(`check`)를 낸다. `--scan`은 저장한 검사 패턴이 다른 글에서 걸리는 곳을 보인다.
- `scripts/check_cross_post.py`: 원고에서 다른 발행 글과 거의 같은 문장(소개 문장, 비유를 옮겨 온 틀 문장)을 찾는다.
- `scripts/recheck_values.py`: 작업 폴더 `recheck.tsv`에 적은 변하는 값(star, 저장소 수, 검색 결과 수, 해커뉴스 점수, 최신 릴리스, PR 상태)을 다시 조회해 원고 값과 다른 것을 알려 준다.
- `scripts/request_index.py`: Search Console 소유자 화면을 Aside로 조작해 주소마다 색인 생성을 요청한다. 화면의 Google 계정이 인자와 다르거나 주소가 속성 밖이면 멈추고, `--no-submit`은 누르지 않고 요청 전 상태만 읽는다.
- 경로는 이 스킬 폴더 기준이다(`<skill-dir>/scripts/...`). 모두 `--help`를 먼저 보고 실행한다.
- Pillow가 필요한 `render_terminal.py`와 여백을 자르는 `render_html.py`는 `uv run --with pillow python3 <skill-dir>/scripts/<스크립트>`로 돌린다.

## 보고

- 단계가 끝날 때마다 사용자가 바로 열 수 있는 미리보기 주소나 파일 경로를 적는다.
- 원고를 보여 주기 전에 `corrections.py check`를 돌리고, 마지막 줄(검사한 교정 수와 걸린 곳 수)을 함께 적는다.
- 확인한 것, 설정만 한 것, 확인하지 않은 것을 나눠 적는다.
