## 근거 표

작업 폴더에 `claims.md`를 두고 원고의 수치와 단정마다 한 줄씩 적는다. 다음 템플릿을 그대로 쓴다.

```markdown
| 원고 문장 | 근거 | 조회일 |
|---|---|---|
| <수치나 단정이 든 문장> | <로그 경로:줄, 실행한 명령, 1차 출처 주소> | <YYYY-MM-DD> |
```

- 시연에서 직접 본 것만 단정한다. 문서나 코드로만 확인한 동작은 "문서 기준"으로 밝히고, 확인하지 않은 동작은 쓰지 않는다.
- 조건이 붙는 주장은 조건을 같은 문장에 쓴다. 예: 비용이 0인 것이 특정 모드에서만 참이면 그 모드를 문장에 넣는다.
- 설치나 갱신 명령을 글에 실으면 그 명령이 파일을 쓰는 위치를 패키지 소스에서 확인해 적는다. 안내 문구만 보고 쓰면 독자의 컴퓨터에서 실제로 바뀌는 범위를 적게 적는다.
- 비교 대상의 특징은 그 제품의 공식 문서로 확인하고, 쓰면 안 되는 과장 표현 목록을 함께 만든다. 비교 작업의 예시가 이 저장소에 있으면 먼저 읽는다.
- 시연 중 실패와 에이전트의 틀린 답은 숨기지 않는다. 무엇이 어떻게 틀렸는지와 바른 값을 함께 적는다.
- 공식 소개 문구끼리 수치가 다르면(README와 패키지 설명의 개수 차이 등) 직접 센 값을 쓰고 차이를 한 줄로 밝힌다.
- 공식 출처끼리 일정, 시간, 장소가 다르면 둘 다 근거 표에 적고, 그 값을 운영하는 곳(행사장은 장소 운영사, 대회는 주최 공지)의 안내로 정한다. 한쪽을 추측으로 버리면 틀린 값을 발행한다.
- 비교 글은 공정성을 따로 본다.
    - 우리 도구가 진 항목도 요약 박스와 마치며에 쓴다. 본문에만 두면 요약만 읽는 독자에게 숨긴 것이 된다.
    - 답을 내려고 바꾼 설정(추론 수준, 인용 켜기, 청크 크기)은 도구마다 모두 밝힌다.
    - 자료를 거부당하는 등 조건이 달라진 결과는 그 조건을 결과 옆에 적는다.
    - 캡처가 표에 센 실행인지 따로 돌린 실행인지 캡션에 적는다.
- 전체 개수와 순위는 정확한 개수를 돌려주는 조회로 센다. 검색 API의 결과 수는 어림값일 수 있다(해커뉴스 Algolia 검색은 `exhaustive.nbHits`가 `false`면 `nbHits`가 어림값이다). 그럴 때는 정확한 값이 나올 만큼 기간을 잘게 나눠 센 뒤 더한다. 예시 스크립트가 이 저장소에 있으면 먼저 읽는다.
- 순위와 전체 수에는 모집단을 함께 적는다(포크 포함 여부, 공개 여부, 기간). 모집단이 빠지면 독자가 같은 숫자를 다른 범위로 읽는다. GitHub 저장소 검색은 기본으로 포크를 빼고 센다.
- 시간이 지나면 바뀌는 값(star, 저장소 수, 검색 결과 수, 해커뉴스 점수, 최신 릴리스, PR 상태)은 작업 폴더의 `recheck.tsv`에 한 줄씩 적는다. 형식은 `recheck_values.py --help`에 있다.
- "아직", "최신", "현재"처럼 날짜 없이 상태를 말하는 문장은 그 상태를 정하는 값(릴리스 태그, PR 상태)을 `recheck.tsv`에 적는다. 새 릴리스 하나로 틀린 문장이 된다.
- `recheck_values.py`는 머지 직전, 공유 글을 쓰기 전, 발행 뒤 수정 때 돌린다. 머지 직전에는 바뀐 값과 기준 날짜를 원고, 그림, 근거 표에서 함께 고친다. 새 릴리스가 나왔으면 바뀐 점이 글과 부딪치는지 보고, 확인한 버전을 글에 적는다.
- 발행 뒤에는 기준 날짜를 붙인 값은 바뀌어도 그대로 둬도 된다. 그날 기준으로는 맞는 값이다. 날짜 없이 상태를 말하는 문장이 바뀌었으면 고친다.
- 행사 글은 날짜별 운영 시간과 장소를 머지 직전에 다시 조회한다. 날짜마다 시간이 다를 수 있어 마지막 날까지 따로 본다.

## 독자와 도입

쓰기 전과 검수 때 아래를 확인한다. 목차 단계에서 정한 기준 독자의 용어 목록으로 원고의 설명 수준을 맞춘다.

- 제목과 본문 첫 세 문장만 읽어도 누구를 위한 글인지와 읽으면 무엇을 얻는지 알 수 있게 쓴다. 효용은 기술 습득뿐 아니라 개념 이해, 새로운 관점, 재미있는 이야기일 수 있다.
- 독자의 장면으로 시작하더라도 효용을 뒤로 미루는 개인 이력이나 역사 설명은 필요한 절로 옮긴다.
- 기준 독자가 모를 용어는 처음 쓰는 자리에서 이 글을 이해하는 데 필요한 만큼 설명한다. 비유에 쓰는 대상도 그 독자가 아는지 확인한다.
- 링크를 누르거나 툴팁을 열지 않고도 처음부터 끝까지 이해할 수 있게 쓴다. 링크는 근거나 심화 자료로 남기고, 이해에 필요한 내용은 본문에 요약한다.
- 연재 글도 이번 글만으로 읽을 수 있게 쓴다. 도입을 지난 편의 회고로 시작하지 말고, 이전 글의 맥락이 필요한 자리에서 핵심만 요약한 뒤 링크한다.

## 독립 검토

원고를 쓴 컨텍스트가 아닌 검토자(서브에이전트나 워크플로)에게 나눠 맡긴다. 검토자에게는 원고 경로, 근거 표 경로, `corrections.py review` 출력(지난 교정 점검표)을 주고, 지적마다 줄 번호와 고칠 문장을 받는다.
구조 검토자에게는 `check_cross_post.py` 출력(아래 다른 글과 겹치는 문장 절)도 준다.

| 검토자 | 보는 것 |
|---|---|
| 사실 | 원고의 주장과 수치를 로그, 1차 출처와 대조한다 |
| 문체 | 이 저장소 플레이북 문체, 브랜드 문서, 전역 AI티 금지 규칙 |
| 이미지 | 잘림, 개인정보, 강조 위치, 그 절이 다루는 대상을 보여 주는 자료인지(플레이북 6절), 도구 화면 캡처 캡션의 날짜와 버전, 남의 이미지 출처와 생성 이미지를 밝혔는지. 사용자가 찍은 사진의 캡션에는 날짜나 출처를 붙이지 않는다 |
| 독자 | 목차 단계의 기준 독자와 용어 목록으로 위 독자와 도입 절을 점검한다. 그 밖에 처음 읽는 비개발자가 막히는 곳, 독자가 쓰지 않는 대상과의 비교, 점수, star, 조회수 같은 숫자 지표에 무엇이 쌓인 값인지와 얼마나 큰지(같은 해 글 중 몇 번째 등)가 붙었는지를 본다. 사이트 이름만 풀어서는 숫자의 뜻이 전해지지 않는다 |
| 이야기 | 이 저장소 조사 문서의 검토 점검표. 장면, 막힘, 해결이 원인과 결과로 이어지는지, 제목과 요약이 한 문장으로 모이는지, 사진 속 모습을 옮긴 문장마다 독자가 얻는 정보가 있는지(플레이북 4절) |
| 구조 | 문장 단위 윤문 도구가 보지 못하는 글 전체의 모양. 같은 사실이 몇 번 나오는지 사실별로 세어 두 번 이상이면 한 곳만 남긴다. 기사나 공식 자료에서 가져온 내용을 직접 겪은 장면처럼 쓴 문장은 근거 표의 출처와 대조해 출처대로 쓴다. 화면, 포스터, 사이트에 적힌 글을 옮겨 적은 문장, 마치며에서 본문을 되풀이하는 요약, 다른 글에서 옮겨 온 틀 문장을 찾는다 |

- 지적을 반영한 뒤 바뀐 주장만 모아 사실 검토를 한 번 더 돌린다.
- 검토자의 지적이 근거와 맞지 않으면 반영하지 않고, 그 이유를 보고에 적는다.

## 윤문과 군더더기

1. 고치기 전 원고를 복사해 둔다(`before.md`). 이미 있으면 덮어쓰지 않고 `before-2.md`처럼 번호를 올린다. 앞선 윤문 전 상태는 그 사본에만 남는다.
2. `humanize-korean`으로 AI 티를 고친다.
3. 없어도 뜻이 같은 문장을 지운다. 앞 절을 되풀이하는 요약, "이 절에서는" 같은 안내 문장, 겸양 마무리, 같은 사실의 두 번째 서술이 대상이다.
4. 독자가 고를 수 있는 것은 "~할 수 있습니다", 하지 않아도 되는 것은 "~하지 않아도 됩니다"로 쓴다. 도구 동작을 사양서처럼 단정하면 번역투로 읽힌다.
5. 동료에게 설명하듯 읽어 보고, 과한 격식과 수동 표현을 구체적인 주어와 동사로 고친다. 예: "본 프로젝트의 진행 과정에서 여러 정적 분석 도구가 활용되었습니다"는 "이 프로젝트에서 정적 분석 도구 몇 가지를 써 봤습니다"로 쓴다. 브랜드의 높임말과 사실의 범위는 유지한다.

## AI 티 2차 탐지

`humanize-korean`이 놓친 AI 티를 patina로 한 번 더 찾는다. 도구마다 보는 패턴 목록이 달라서다. 탐지를 게이트로 두고, 게이트에 걸린 곳 중 문장 수정으로 풀리지 않는 문단만 재작성으로 넘긴다.

1. 원고 전체를 탐지만 돌린다. 글 한 편에 몇 분 걸린다.
    ```bash
    bunx patina-cli --audit --backend claude-cli --lang ko --document-type blog src/content/posts/<slug>.md
    ```
2. 결과 표의 패턴과 위치를 하나씩 보고, 문장을 고쳐 풀리는 곳은 직접 고친다.
3. 문장 몇 개를 고쳐서는 안 되고 문단을 통째로 다시 써야 하는 곳만 그 문단을 작업 폴더의 파일로 잘라 재작성한다. 글 전체를 넘기면 `claude`가 출력 한도를 생각에 다 써서 끝나지 않는다.
    ```bash
    bunx patina-cli --verify --backend claude-cli --lang ko --document-type blog <문단>.md > <문단>.new.md
    ```
    - 다시 쓴 문단은 표준 출력으로만 나오고 원래 파일은 그대로다.
    - 종료 코드가 4면 의미 보존 하한을 넘지 못한 것이다. 결과를 버리고 그 문단은 직접 고친다.
4. 재작성 결과는 `diff <문단>.md <문단>.new.md`로 원래 문단과 대조한 뒤 원고에 넣는다. 예시가 좁아지거나("카카오톡이나 슬랙처럼"이 "카카오톡이나 슬랙은"으로), 동사가 흐려지거나, 높임이 빠지거나, 제품명 표기가 바뀌어도 patina의 의미 보존 점수는 통과로 나온다.
5. 넣은 문단을 1번 명령으로 다시 탐지해 새로 걸린 패턴이 없는지 본다.

- 명령마다 `--backend claude-cli`를 붙인다. 빼면 기본 백엔드인 OpenAI API로 원고가 나가고 비용이 든다.
- 탐지에서 걸린 곳이 없으면 재작성하지 않는다. patina도 이미 자연스러운 글을 다시 쓰면 AI 티가 늘 수 있다고 경고한다.

## 지난 교정 검사

윤문과 재작성이 사용자가 고쳐 준 모양을 되살리거나 표현만 바꿔 되살릴 수 있으므로 AI 티 2차 탐지 뒤에 돌린다.

```bash
python3 <skill-dir>/scripts/corrections.py check src/content/posts/<slug>.md
```

- 걸린 곳마다 나오는 이유와 고친 예를 보고 고친 뒤, 걸린 곳이 0이 될 때까지 다시 돌린다.
- 문맥상 그 교정에 해당하지 않으면 그대로 두고 이유를 보고에 적는다. 같은 오탐이 되풀이되면 `edit`로 패턴을 좁힌다.

## 다른 글과 겹치는 문장

글마다 같은 소개 문장이나 비유를 되풀이하면 틀에서 찍어 낸 글로 읽힌다. 윤문 도구와 지난 교정 검사는 한 글만 보므로 이 반복을 잡지 못한다.

```bash
python3 <skill-dir>/scripts/check_cross_post.py src/content/posts/<slug>.md
```

- 걸린 문장은 이 글의 맥락에 맞게 다시 쓰거나 지운다. NomaDamas 소개 문장이면 지운다. 소개는 글 끝 공용 블록이 맡고, 본문에는 이 글의 주제와 이어지는 NomaDamas 사실만 남긴다(플레이북 7절).
- 다른 글 절반 이상에 나오는 공통 문구(AI 보조 고지 같은 것)는 개수만 센다.
- 기본 유사도 0.8은 숫자만 다른 같은 틀의 문장(star 수 소개)을 뺀다. 틀 자체가 의심되면 `--threshold 0.7`로 넓혀 본다.

## 바뀌면 안 되는 것 확인

윤문과 군더더기 정리가 끝나면 이번 윤문 전 사본과 스크립트로 비교한다. 사본에 번호를 올렸으면 가장 최근 사본을 넘긴다.

```bash
python3 <skill-dir>/scripts/check_post_invariants.py <윤문 전 사본> src/content/posts/<slug>.md
```

- 오류(종료 코드 1)는 고친 뒤 다시 돌린다: frontmatter의 값 필드(날짜, 태그, 이미지 등), 코드 블록, 이미지 참조가 바뀌었거나 금지 기호가 있다.
- 경고는 하나씩 본다: 다듬은 `title`, `description` 문장, 사라졌거나 새로 생긴 링크, 인라인 코드, 숫자. 중복 문장을 지워 사라진 것이면 그대로 두고, 뜻이 바뀐 것이면 되돌린다.
- 연결어미 뒤 쉼표 경고는 쉼표를 뺀다. 빼면 앞뒤 말이 한 덩어리로 잘못 읽히거나("묻지 않고 폴더 밖 접근을 막는") 세 절 이상이 한 문장에 이어지면 마침표로 나눈다. 비교는 새로 생긴 쉼표만 알리므로, 발행한 글에 남은 쉼표를 지울 때는 `--commas`로 원고 하나의 쉼표를 문맥과 함께 모두 보고 하나씩 판단한다. 사용자가 쉼표를 지적해도 교정 표에 정규식 검사 행을 따로 만들지 않는다. 이 스크립트가 명사 예외(참고, 최고, 개발자)까지 두고 같은 일을 하고, 거친 정규식은 다른 글의 명사까지 잡는다.
- 이미지나 영상이 없는 절 경고는 그 절이 다루는 대상을 보여 주는 자료를 넣어 푼다. 표나 코드 블록으로 충분한 절(시작하기 명령, 비교표)이면 그대로 두고 이유를 보고에 적는다.
- 물결표 경고는 범위를 "부터, 까지"로 풀어 쓴다. 짝이 맞는 물결표 사이는 본문에서 취소선이 되고, 이미지 대체 텍스트에서는 물결표가 지워진다.
- 윤문 없이 볼 때는 원고 하나만 넘긴다. 금지 기호와 위 두 경고를 본다.
- 발행 뒤 수정은 발행본과 비교한다(`publish.md` 발행 뒤 수정 절).
