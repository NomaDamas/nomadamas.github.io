# 검색 노출: 점검과 측정

블로그가 검색에 안 나오는 원인을 찾고, 기술 상태, 웹마스터 도구 실적, 검색 수요, AI 답변 인용을 서로 다른 관측으로 기록한다. 이 저장소의 검색 관련 이슈(`gh issue list --search 검색`)와 플레이북을 먼저 읽는다. 좌표, 권한, 토큰 받는 법은 이 저장소의 운영 문서가 정본이다.

- 검색에 안 나오는 원인을 물으면 "막힌 단계 찾기"까지 하고 고칠 조치를 제안한다.
- 실적, 검색 수요, 글 후보를 물으면 "측정"을 한다. 검색 수요로 글 주제를 고르는 요청도 여기다.

## 목차

- 막힌 단계 찾기
- 측정
- 판정
- 산출물

## 막힌 단계 찾기

검색 노출은 공개, 발견, 크롤링, 색인, 노출, 클릭 순서로 일어난다. 처음 막힌 단계부터 고친다. 앞 단계가 막혀 있으면 뒤 단계(키워드, 제목)를 고쳐도 효과가 드러나지 않는다.

| 단계 | 무엇으로 보나 | 막혔을 때 |
|---|---|---|
| 공개 | `search-baseline.py`의 `site` 모드: 주소 응답, robots.txt, canonical, 사이트맵 | 블로그 설정을 고친다 |
| 발견 | URL 검사의 참조 사이트맵과 참조 페이지, 사이트맵 API | 아래 사이트맵 진단, 들어오는 링크 |
| 크롤링 | URL 검사의 `lastCrawlTime` | 색인 생성 요청(`seo-geo.md` "발행 뒤 알림과 색인 요청") |
| 색인 | URL 검사의 `coverageState` | 중복, canonical, 본문 품질 |
| 노출 | 검색 실적의 페이지별 노출 | 키워드 자리(`seo-geo.md` "검색 키워드 점검") |
| 클릭 | 노출 대비 클릭 | 제목과 설명문 |

- 사이트맵 색인 파일이 "성공"이어도 하위 사이트맵을 처리하지 않을 수 있다. 화면에는 "발견된 페이지 0"으로 보이고, 사이트맵 API 응답에서는 색인 파일의 `contents`가 비어 있다.
    - 그러면 하위 사이트맵 주소를 사이트맵 API로 따로 묻는다. 404("not a submitted or a known sitemap")면 Google이 모르는 것이다.
    - 하위 사이트맵을 직접 제출한다. 서비스 계정의 '제한적' 권한으로는 안 되고 소유자 화면(Sitemaps > 새 사이트맵 추가)에서 한다. 사이트 제출이라 승인받는다.
- URL 검사의 참조 사이트맵과 참조 페이지가 둘 다 비어 있으면 발견 단계에서 막힌 것이다. 사이트맵 진단과 함께 블로그로 들어오는 링크를 본다. 우리 소유 페이지(조직 사이트, 저장소 README)에서 블로그로 가는 링크부터 확인한다.
- 네이버와 Bing은 IndexNow 응답과 각 웹마스터 도구의 수집 현황으로 발견 여부를 본다. IndexNow 200, 202는 접수일 뿐 색인 완료가 아니다.

## 측정

1. 기존 발행 글과 이 저장소 작업 폴더의 기준선을 찾아 같은 주제와 질의가 있는지 확인한다.
2. 이 저장소에 검색 기준선 스크립트가 있으면 `--help`로 지원 모드를 확인한다. 없으면 공개 응답과 웹마스터 도구를 직접 읽고 조건을 기록한다.
3. `site` 모드로 공개 응답, 사이트맵, RSS, 글 메타데이터를 수집한다.
4. 검색 API 결과로 순위나 색인을 재지 않고, 그 결과를 저장하지 않는다.
    - 대상: 네이버 검색, Brave, Exa. 스크립트의 `naver`, `brave` 모드와 그 모드를 부르는 러너도 포함한다.
    - 이유: 네이버 검색 API 특약 2.3은 결과와 파생물의 저장, AI 입력을 막고, Brave 약관 3(b)(i)은 일시 저장 밖의 저장을 막는다. 원문과 확인 시각은 이 저장소 작업 폴더에 기록한다.
5. 질의별 노출, 클릭, 평균 순위와 주소별 색인 상태는 웹마스터 도구에서 읽는다.
    - Search Console: 서비스 계정으로 API를 부른다. 질의 실적과 홈, 글 주소의 색인 상태는 gh-org-dashboard의 `search_*` 테이블에 매일 쌓인다. 테이블이 비었거나 오래됐으면 API로 직접 본다.
    - Bing: Webmaster API 키가 있으면 API로, 없으면 Webmaster 화면을 `aside-browser`로 읽는다. 키 상태는 이 저장소 운영 문서에서 확인한다.
    - 네이버 서치어드바이저: `aside-browser`로 관리 화면을 읽는다.
6. 웹마스터 도구마다 속성, URL 범위, 기간, 보고서 갱신 시점을 기록한다.
7. `datalab` 모드는 시작일과 종료일을 명시한다. 인증은 `agents-env run NAVER_CLIENT_ID NAVER_CLIENT_SECRET --`로 주입한다.
8. Google Trends는 로그인하지 않은 `camoufox` 프로필로 열고, 동일 지역/기간/검색 유형으로 비교해 화면의 CSV 다운로드를 보존한다.
9. 연결하지 못한 웹마스터 도구는 `not_measured`와 이유를 기록한다.
10. 결과는 이 저장소가 정한 검색 측정 작업 폴더에 새 폴더로 저장한다. 기존 결과를 덮어쓰지 않는다. 이 저장소의 최신 `origin/main`에서 만든 브랜치에 커밋해 PR로 올린다.
11. 기존 글과 겹치지 않는 후보를 최대 3개 제시한다. 사용자가 고르면 `SKILL.md` 흐름의 2단계(주제 정하기)로 넘긴다.

## 판정

- 수집 스크립트의 HTTP 오류와 비정상 종료는 측정 실패다. 결과 없음으로 바꾸지 않는다.
- 웹마스터 도구의 평균 순위는 노출이 생긴 질의만의 값이다. 노출 0은 미색인 판정이 아니고, 색인 여부는 색인과 수집 보고서로 따로 본다.
- 브랜드 언급과 소유 도메인 URL, 제3자 인용은 별도 열로 나눈다.
- 도메인 속성의 전체 실적을 블로그 실적으로 옮기지 않는다. 페이지별 URL을 확인한다.
- 데이터랩/Trends 지수는 상대값이다. 누락 구간은 수요 0이 아니며, 별도 요청의 지수를 그대로 합치지 않는다.
- 미완료 주와 완료 주를 구분한다. RAG처럼 다른 뜻도 있는 검색어는 관련 질의와 함께 해석한다.
- 주 단위 보고는 `09-docs/os-spec.md`의 화요일 경계를 따른다. 일 단위로 받는 실적은 그 경계로 다시 묶고, 주 단위로만 받는 지수는 그 도구의 주 시작일을 함께 적는다.
- 공개 페이지 HTTP 200, sitemap 제출 성공, 색인 완료, 클릭 발생은 각각 다른 상태다.
- AI 답변의 브랜드 언급과 실제 인용 URL은 제품/모델/질문/시각을 기록해 직접 확인한다. 검색 API를 AI 앱 답변으로 대체하지 않는다.
- 계정 등록, 사이트 제출, 발행, 유료 API 호출은 조회와 분리하고 해당 실행 승인이 있는지 확인한다.

## 산출물

다음 형식으로 보고한다. 사이트 점검, 웹마스터 도구, 데이터랩의 원본 응답과 요청 조건은 보고서와 함께 보존한다.

```text
대상 / 조회 시각 / 보고 기간
막힌 단계:
관측 | 범위 | 결과 | 원본 파일 | 한계
기술 상태:
웹마스터 도구:
검색 수요:
AI 답변 인용:
콘텐츠 후보: 독자 / 질문 / 기존 글과 차이 / 근거 / 필요한 실습
```

완료 조건은 성공한 수집과 실패한 수집이 모두 기록되고, 수치마다 범위와 원본이 연결되는 것이다.
자동 스케줄 등록은 이 작업이 아니다. 주기 운영은 저장소의 시스템 운영 지침을 따른다.
